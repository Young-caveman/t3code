# Custom fork host setup

Runbook for the `yash/swiftui-orchestrator-v2-support` fork, which keeps the official release
version `0.0.42` while replacing the orchestrator with V2. Read this before touching either host.

The one invariant: **the desktop app and the CLI runtime on every SSH target must be built from the
same revision.** A fork that does not change its version number breaks this silently, because every
downloader still resolves the official artifact for `0.0.42`.

## Hosts

|             | macOS                                  | Linux (Omarchy)                           |
| ----------- | -------------------------------------- | ----------------------------------------- |
| Source      | `/Users/jimmy/coding/t3code`           | `/cave/t3code`                            |
| Branch      | `yash/swiftui-orchestrator-v2-support` | same                                      |
| Built from  | `54883344f9`                           | same                                      |
| App         | `/Applications/T3 Code (Alpha).app`    | `~/Applications/T3 Code/T3 Code.AppImage` |
| T3 home     | `~/.t3`                                | `~/.t3`                                   |
| CLI runtime | `~/.t3/runtime/versions/0.0.42/t3`     | same path                                 |

"Built from" is the revision the installed app and runtime were compiled from, not a permanent pin on
`HEAD`. `origin` is `git@github.com:Young-caveman/t3code.git`, `upstream` is
`https://github.com/pingdotgg/t3code.git`.

The T3 home paths are independent per host and do not have to match. `T3CODE_HOME` only decides
where a process reads and writes state. What has to match is the code that mints an auth token and
the code that verifies it.

## Problems this solves

### 1. SSH bootstrap fails with 401

```text
DesktopSshEnvironmentRequestError: [ssh_http:401] SSH remote API request failed during bootstrap-bearer-session
```

The runner generated by `packages/ssh/src/tunnel.ts` writes a small script to the remote and runs:

```sh
run-t3.sh auth pairing create --base-dir "$HOME/.t3" --json
```

`run-t3.sh` resolves `~/.t3/runtime/versions/$T3_ARCHIVE_VERSION/t3`, and when that directory is
missing it downloads from the official release URL. The official `0.0.42` CLI writes
`auth_pairing_links` into `userdata/state.sqlite`, while the V2 server reads
`userdata/statev2.sqlite` (`apps/server/src/config.ts`). The pairing record is therefore invisible to
the server and the exchange returns `401 invalid_credential`.

Confirm the mismatch on the SSH target by running the runner's own command and watching which
database changes:

```sh
sqlite3 ~/.t3/userdata/statev2.sqlite 'select count(*) from auth_pairing_links;'
~/.t3/ssh-launch/<state-key>/run-t3.sh auth pairing create --base-dir ~/.t3 --json
sqlite3 ~/.t3/userdata/statev2.sqlite 'select count(*) from auth_pairing_links;'
```

If only `userdata/state.sqlite` grows, the target is still running an official CLI. The runner script
lives on the target, not on the desktop host, and is rewritten on every bootstrap.

### 2. Mixed official and fork installs in one T3 home

A T3 home that holds both an official CLI runtime and a fork app can authenticate against whichever
code happens to run. Two rows in `auth_pairing_links`, one in each database, is the signature.

### 3. Dead rows in the legacy database

`userdata/state.sqlite` is not read by the V2 server at all. Old pairing rows and old sessions there
are inert. They are safe to delete, and they are also safe to leave; deleting them is only for a
clean slate.

### 4. The runtime silently reverts

The runner reuses an installed runtime only when both conditions hold:

```sh
[ -x ~/.t3/runtime/versions/0.0.42/t3 ] && \
  [ "$(cat ~/.t3/runtime/versions/0.0.42/.install-complete 2>/dev/null)" = "0.0.42" ]
```

Delete that directory, or leave a stale `.install-complete`, and the next SSH connection downloads the
official CLI and the 401 comes back.

## Safety rules

- Back up before deleting: `tar -czf ~/t3-userdata-backup-$(date +%s).tar.gz -C ~/.t3 userdata`.
- Keep `~/.t3/userdata/secrets` and `settings.json` if the host should keep provider logins.
- Kill only a PID you captured at spawn, or one whose `/proc/<pid>/cwd` you checked. Never
  `pkill -f t3`, `pgrep | kill`, or kill by app name; other T3 instances are running on these hosts.
- Never delete or copy `state.sqlite` between hosts to "fix" auth.
- Do not commit tokens, pairing credentials, or `secrets/` contents.

## Step 1: sync the source

```sh
cd /Users/jimmy/coding/t3code
git fetch origin
git checkout yash/swiftui-orchestrator-v2-support
git pull --ff-only
git rev-parse --short HEAD   # must match the revision the app and runtime were built from
```

The same revision has to be checked out on every host, because the app and the CLI runtime are both
built from it. Record the value; later steps compare against it rather than against a hash written
here.

If `git fetch origin` fails with `Permission denied (publickey)`, the machine has no working GitHub
credentials. Fetch from the other host's checkout over the SSH alias that does work:

```sh
git remote add omarchy omarchy:/cave/t3code
git fetch omarchy yash/swiftui-orchestrator-v2-support
git merge --ff-only FETCH_HEAD
```

`git status` will then report the branch as ahead of `origin`, because the `origin` tracking ref is
stale and unreachable. That is expected; do not switch remotes to silence it.

If the app and runtime have to be rebuilt, also install dependencies with `vp i` and make sure a Rust
toolchain is on `PATH` (`cargo --version`); the resource monitor is a Rust crate.

## Step 2: verify or build the CLI runtime

Check what is already installed before rebuilding anything:

```sh
ls -la ~/.t3/runtime/versions/0.0.42/
cat ~/.t3/runtime/versions/0.0.42/.install-complete
~/.t3/runtime/versions/0.0.42/t3 --version
shasum -a 256 ~/.t3/runtime/versions/0.0.42/t3
```

The layout must contain `t3`, `client/`, `resource-monitor/`, `node_modules/`, and an
`.install-complete` holding exactly `0.0.42`. If it does, skip to Step 3.

To build it from the current revision:

```sh
cd /Users/jimmy/coding/t3code
vp run build:resource-monitor
vp env exec --node 26.8.1 node apps/server/scripts/cli.ts build-exe --target darwin-arm64
node scripts/build-cli-archive.ts \
  --platform mac --arch arm64 --version 0.0.42 \
  --output-dir /tmp/t3-yash-cli \
  --resource-monitor-dir native/resource-monitor/target/release
```

`build-cli-archive` is what produces the unit the runner expects: a gzipped tar with a single
top-level `t3-0.0.42-darwin-arm64/` directory. On Linux the same script runs with
`--platform linux --arch x64`.

Install it the way the runner would, so a later bootstrap reuses it instead of downloading:

```sh
VERSION=0.0.42
mkdir -p ~/.t3/runtime/versions
RUNTIME_DIR="$HOME/.t3/runtime/versions/$VERSION"
STAGING="$(mktemp -d "$HOME/.t3/runtime/versions/.staging-XXXXXX")"
tar -xzf /tmp/t3-yash-cli/t3-$VERSION-darwin-arm64.tar.gz -C "$STAGING" --strip-components=1
"$STAGING/t3" --version            # refuse to install a binary that cannot run here
printf '%s\n' "$VERSION" > "$STAGING/.install-complete"
rm -rf "$RUNTIME_DIR"
mv "$STAGING" "$RUNTIME_DIR"
```

Then re-check `--version`, `.install-complete`, and the hash.

## Step 3: verify or install the desktop app

macOS: confirm the bundle is the fork build and reports the fork's version.

```sh
defaults read "/Applications/T3 Code (Alpha).app/Contents/Info.plist" CFBundleShortVersionString
```

The Electron user-data profile is `~/Library/Application Support/t3code-v2` **by design** for this
branch (`apps/desktop/src/app/DesktopUserData.ts`). It is not a leftover install and not a bug. Do
not delete it while troubleshooting, and do not rename it to "fix" a path.

Linux: the AppImage comes from

```sh
cd /cave/t3code && vp run dist:desktop:linux   # release/T3-Code-0.0.42-x86_64.AppImage
```

and is launched through a wrapper that pins the T3 home, because the desktop entry cannot pass
environment variables reliably:

```sh
#!/bin/sh
exec env T3CODE_HOME=/home/caveman/.t3 "/home/caveman/Applications/T3 Code/T3 Code.AppImage" "$@"
```

Launch the app and confirm the embedded server is listening:

```sh
ss -H -ltnp | grep ':3773'
```

## Step 4: remove leftovers

Only after Step 2 and Step 3 are verified. Take the backup first.

On the desktop host:

```sh
# legacy V1 database, unused by the V2 server
rm -f ~/.t3/userdata/state.sqlite ~/.t3/userdata/state.sqlite-wal ~/.t3/userdata/state.sqlite-shm

# any runtime version that is not the current app version
ls ~/.t3/runtime/versions/
```

On each SSH target, the runner's bookkeeping is regenerated on the next ensure and is safe to drop:

```sh
rm -rf ~/.t3/ssh-launch
```

Do not remove `userdata/secrets`, and do not remove `userdata/statev2.sqlite` unless the host should
start from an empty project and thread history.

## Step 5: verify the SSH path end to end

The remote server must be running first. With the remote app stopped, the tunnel reports
`channel 2: open failed: connect failed: Connection refused`, which is not an auth problem.

Run this from the desktop host. It performs exactly what the app performs: pairing credential over
SSH, tunnel, token exchange, authenticated readback, and cleanup.

```sh
set -euo pipefail
PORT=59999
TUNNEL_PID=""

cleanup() {
  if [ -n "$TUNNEL_PID" ] && kill -0 "$TUNNEL_PID" 2>/dev/null; then
    kill "$TUNNEL_PID" 2>/dev/null || true
    wait "$TUNNEL_PID" 2>/dev/null || true
  fi
  if [ -n "${PAIRING_ID:-}" ]; then
    ssh -o BatchMode=yes omarchy '$HOME/.t3/runtime/versions/0.0.42/t3' \
      auth pairing revoke --base-dir '$HOME/.t3' "$PAIRING_ID" >/dev/null 2>&1 || true
  fi
}
trap cleanup EXIT

PAIRING_JSON="$(ssh -o BatchMode=yes omarchy \
  '$HOME/.t3/runtime/versions/0.0.42/t3' auth pairing create --base-dir '$HOME/.t3' --json)"
CREDENTIAL="$(printf '%s' "$PAIRING_JSON" | python3 -c 'import json,sys; print(json.load(sys.stdin)["credential"])')"
PAIRING_ID="$(printf '%s' "$PAIRING_JSON" | python3 -c 'import json,sys; print(json.load(sys.stdin)["id"])')"

ssh -o BatchMode=yes -o ExitOnForwardFailure=yes -N -L "$PORT:127.0.0.1:3773" omarchy &
TUNNEL_PID=$!
for _ in $(seq 1 50); do nc -z 127.0.0.1 "$PORT" 2>/dev/null && break; sleep 0.2; done

RESPONSE="$(curl -sS -w '\n%{http_code}' -X POST "http://127.0.0.1:$PORT/oauth/token" \
  -H 'content-type: application/x-www-form-urlencoded' \
  --data-urlencode 'grant_type=urn:ietf:params:oauth:grant-type:token-exchange' \
  --data-urlencode "subject_token=$CREDENTIAL" \
  --data-urlencode 'subject_token_type=urn:t3:params:oauth:token-type:environment-bootstrap' \
  --data-urlencode 'requested_token_type=urn:ietf:params:oauth:token-type:access_token')"
STATUS="$(printf '%s' "$RESPONSE" | tail -n1)"
BODY="$(printf '%s' "$RESPONSE" | sed '$d')"
[ "$STATUS" = "200" ] || { echo "token exchange failed: $STATUS"; echo "$BODY"; exit 1; }
ACCESS_TOKEN="$(printf '%s' "$BODY" | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')"

curl -sS "http://127.0.0.1:$PORT/api/auth/session" -H "authorization: Bearer $ACCESS_TOKEN"
```

Expected: the token exchange returns `200` and the readback prints `"authenticated":true` with the
orchestration scopes. The `trap` revokes the test credential and closes the tunnel on any exit,
including failure.

A failed bootstrap does not invalidate the saved environment or its catalog entry, so correcting the
runtime is normally the whole fix: the next attempt the desktop makes succeeds. Re-adding the
environment by hand is a fallback for when the app lists no saved environment at all, not a required
step after a `401`.

## Gotchas

- **`415` is not `401`.** `AuthTokenExchangeRequest` is `HttpApiSchema.asFormUrlEncoded`
  (`packages/contracts/src/auth.ts`). A JSON body is rejected as an encoding error, so a hand-written
  probe that sends JSON proves nothing about auth.
- **A successful `bootstrapRemoteBearerSession` against `127.0.0.1:<port>` is not proof.** The local
  host's own server uses the same span name. A real remote check shows a forwarded local port, and
  `auth_sessions` gains a `one-time-token` subject.
- **Matching versions are not matching builds.** Both hosts report `0.0.42`; only the hashes prove
  the fork build is in place.
- **The runner rewrites its own script** in `~/.t3/ssh-launch/<state-key>/run-t3.sh` on every
  bootstrap, so editing that file locally does not stick.
- **Logs.** Desktop traces are `~/.t3/userdata/logs/desktop.trace.ndjson`, one JSON object per line;
  spans such as `ssh.environment.ensure` and `clientRuntime.authorization.bootstrapRemoteBearerSession`
  carry the outcome.

## Definition of done

- Both hosts are on the same source revision, and the app and the CLI runtime were built from it. The
  binaries currently installed were built from `54883344f9`; a later commit that only touches docs does
  not require a rebuild, but a commit that touches `apps/server` or `packages/ssh` does.
- `~/.t3/runtime/versions/0.0.42/t3 --version` reports `0.0.42` and its hash matches the locally built
  binary on that platform.
- `.install-complete` contains `0.0.42`.
- Running the runner's pairing command raises the `auth_pairing_links` count in `statev2.sqlite`.
- The Step 5 probe returns `200` and `authenticated:true`.
- No live `state.sqlite` auth rows are involved anywhere in the flow.
